# 成稿改造特有的踩坑与规避

本文件只记「对已交付 xlsx 改文案」这一场景的新坑。通用的 XML 直改硬规则 X1 到 X18、数据纪律 D1 到 D7 见 `亚马逊表格工作流` 技能，本技能直接复用，不重复。

## P1. 自闭合单元格会吞掉后一格（最高频）

**症状**：用全局正则 `(<c r="([A-Z]+\d+)"([^>]*)>)(.*?)(</c>)` 做 `re.sub`，某个目标格报 `cell not found`，或改完发现相邻格文字串了。

**根因**：空单元格写成 `<c r="B4" s="67"/>`。正则的 `([^>]*)` 会吃到结尾的 `/`，把 `>` 当开标签结束，随后 `(.*?)` 一直找到下一个 `</c>`，也就是 **A5 的结束标签**，于是 A5 被吞进 B4 的匹配里。

**规避**：按目标坐标逐个精确 `re.search`，并在匹配后检查属性是否以 `/` 结尾。

```python
pat = re.compile(r'(<c r="' + ref + r'"([^>]*?)>)(.*?)(</c>)', re.S)
mo = pat.search(raw)
if not mo:
    raise RuntimeError('cell not found: ' + ref)
open_tag, attrs, body, close_tag = mo.groups()
if attrs.rstrip().endswith('/'):
    raise RuntimeError('self-closing cell: ' + ref)
```

`scripts/inspect_workbook.py` 与 `scripts/rewrite_cells.py` 一律用 `xml.etree.ElementTree` 或按坐标精确匹配，不用全局单元格正则。

## P2. 体检脚本的「孤立数字」是假象

用有 P1 问题的正则做 dump，会把 A3、A4、A5 的 sharedStrings 索引显示成 B2、B3、B4 的值，看起来像表里散落着 `2`、`3`、`5`、`77`、`240` 这类纯数字。

**不要把它们当成模板残留去清理**。用 ElementTree 重新读一遍即可确认这些格子本来是空的。某宠物服饰报告体检时出现过这个误判，计划里还专门列了「孤立数字是否清理」的确认项，实际文件里根本没有这些数字。

## P3. sharedStrings 的 count 与 uniqueCount

| 属性 | 含义 | 改写后 |
|---|---|---|
| `count` | 全工作簿 `t="s"` 单元格的引用总数 | **不变**，因为没增删单元格 |
| `uniqueCount` | `<si>` 条目数 | 原值 + 改写格数 |

每个改写格追加一个独立 `<si>` 并只改自己的 `<v>`（X11）。**绝不修改或复用已有 `<si>`**，否则所有引用同一索引的格子会一起变。

漏改 `uniqueCount` 会触发 Excel 的「发现不可读取的内容」修复提示。文本里的换行写成 `&#10;`，转义顺序是先替换 `&`、`<`、`>`，再把 `\n` 换成 `&#10;`，否则换行符会被二次转义成字面文本。

## P4. 文件被 WPS 或 Excel 独占打开

**症状**：`os.replace` 报 `[WinError 5] 拒绝访问`，`shutil.copyfile` 报 `PermissionError 13`。

**降级链**（X6）：重试 `os.replace`、再试 `copyfile` 原地覆盖、最后保留 `.tmp` 并请用户关闭占用。每次写完都要重新读取验证，不能只信返回值。

**不要借 WPS COM 的 `SaveAs` 指向目标路径**。一次实测事故中，WPS 同时开着多个工作簿，`GetActiveObject("Ket.Application")` 拿到的 `ActiveSheet` 是目标文件，但 `ActiveWorkbook` 与 `Worksheet.Parent` 指向另一个 9 Sheet 调研报告，一次 `SaveAs` 把那份报告覆盖到了目标路径，原文件被换掉。

正确顺序：

1. 动手前先生成并保留一份完整快照。
2. 用 `Windows.Item(i).Close($false)` 关闭标题为目标文件名的窗口，释放句柄。
3. 文件级覆盖写回快照。
4. 逐项校验。
5. 需要时用 `Workbooks.Open` 重新打开给用户看。

**更省事的做法**：本技能本来就另存新文件、原件不动，绝大多数情况下不会碰到占用问题；只有用户明确要求覆盖原文件时才需要处理。

## P5. 图片完整性要按字节比对，不能只数数量

`xl/cellimages.xml`、`xl/_rels/cellimages.xml.rels`、每个 `xl/media/*`、每个 `xl/drawings/drawingN.xml` 逐条比对原文件与新文件的 bytes，差异数必须为 0。只数图片张数会漏掉图片内容被换掉或重编码的情况。注意 zip 里可能还有 `xl/media/` 这样的目录条目，统计张数时要排除以 `/` 结尾的条目。

同时比对 DISPIMG 公式数量（在所有 `sheetN.xml` 里数 `DISPIMG` 字样）。

## P6. 未改写的工作表必须字节完全一致

原始数据表、利润测算表这类整表不动的 Sheet，其 `sheetN.xml` 应做到 `za.read(path) == zb.read(path)`。这是比「抽查几个单元格」更强的保证，能证明没有误伤。

## P7. 品牌残留要分类再判断

校验脚本报出品牌名时，先分四类：分析文案、原始数据表、listing 标题与 URL、合规检索清单。只有第一类应该清零。后三类是有意保留，交付时说明，不要为了「数字好看」把它们删掉。

## P8. 两个字数口径别混用

- **被改写文案字数**：只统计映射里的格子，改前与改后对比，用来报告力度。
- **全文件字数**：所有文本单元格。原始数据表与超长商品 URL 通常占 70% 以上，精简后只降不到 1%，这是正常的。

用全文件字数算保留率会得出「几乎没改」的错误结论，也会让用户误以为没做事。

## P9. 映射漏键不会报错，但会留下旧文案

改写引擎只处理映射里列出的格子。若本该改的格没进映射，它会**保留原文且校验全绿**，用户看到的就是旧结论混在新版里。

规避：体检后把「长文本清单」逐条过一遍，明确每条是「改」还是「有意保留」；交付前用 `scripts/verify_rewrite.py` 打印非目标文本格的变化数，必须为 0，同时人工抽查几处长总结格。

## P10. 计划阶段的只读承诺

用户说「先列计划，确认后再改」时，体检脚本只能读、不能写；不要提前备份、不要生成临时副本、不要调用任何改写工具。计划里明确写「没有改动任何文件」，等用户确认后再进入步骤 3。
